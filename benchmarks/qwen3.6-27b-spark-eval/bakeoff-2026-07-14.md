# Qwen3.6-27B overnight bake-off: agent-conditions re-eval (2026-07-14)

Full re-evaluation of four vision-capable Qwen3.6-27B variants on the same GB10 box (128 GB unified memory), this time under production agent conditions rather than the May throughput-oriented setup. Goal: pick the smartest model for a local personal-assistant agent (tool calling, Russian dialogue, vision, long context), with thinking enabled everywhere and no output-token caps.

Run window 2026-07-13 19:13 → 2026-07-14 08:41, fully scripted (launch → bench → suite → next model → restore prod).

## What changed vs the May eval

| | May run | This run |
|---|---|---|
| tool-eval-bench | v1.6.0, temp 0, 3 trials | v2.0.6, temp 1.0 / top-p 0.95 / top-k 20 (prod sampling), seed 42, 1 trial |

| Output budget | default | uncapped (32768 runaway fuse); token spend is a first-class metric |
| Extra suites | spec-bench throughput | GSM8K@1024 (budget discipline), confabulation resistance, Russian digests, vision via data-URI, long-context 59K/177K/245K |

Constant across all four candidates: vLLM `0.25.1.dev24`, one model at a time, identical chat template ([froggeric v21.3](https://huggingface.co/froggeric/Qwen-Fixed-Chat-Templates)), `--reasoning-parser qwen3`, `--tool-call-parser qwen3_xml`, thinking ON, `gpu-memory-utilization 0.50`, `max-num-seqs 4`, all test data synthetic.

The 88-90 tool-eval spread is 1-3 scenarios on a single trial - noise. On tool quality all four are one league; what separates them is the cost and speed of thinking.

Key observations:

- **Verbosity is the real differentiator.** The vanilla builds are not dumber - they think 2-4x longer. Under a hard 1024-token budget (GSM8K plugin hardcodes it) the short thinkers score 90-92.5% while the verbose ones drown in truncation (62.5-72.5%). In an interactive agent with per-request budgets this reads as stupidity; uncapped it reads as latency.
- **Fast silicon loses to a short mind.** NVFP4 decodes 33% faster yet arrives at answers last (median 175 s vs ThinkingCap's 74 s), because it thinks 4.6x longer. Its p90 of 594 s is a single CoT ballooning to 19.7K tokens.
- **TC-60 (cross-turn sleeper injection) remains a base-model weakness** - the official FP8 was the only build to deflect it this time (May run: every variant failed it). Single trial; treat as noise until re-tested.
- **Long-context (up to 245K real tokens, needle + aggregation):** retrieval is clean on all four; each missed exactly one event-counting question (answered 11 or 13 vs ground truth 12).
- Ground truths were verified independently (grep for counts, Python for arithmetic); every FAIL was reviewed by hand against raw outputs. One error in my own ground truth (vision count) was caught and fixed before the run.

## Epilogue: benchmarks vs production (the honest part)

Per the numbers above, ThinkingCap won the night (parity quality, fewest tokens, fastest answers) and went to production the same morning. **It lasted ~2.5 hours.** In real agent use it repeated tasks and mislogged a food-diary entry ("beer" instead of "coffee"). Bench parity did not survive contact with reality; the Opus-trace tune remains noticeably more attentive in live multi-turn agent work. Rolled back to Qwopus v2.

Two durable outcomes did come out of the bake-off:

1. **Chat template fix.** Qwopus's only weak category was C (multi-step chains, 4/8). Its author had already fixed the template upstream (commit `2ea14ba`, 2026-06-23): past tool calls are now serialized as JSON inside `<tool_call>` instead of XML `<function=>/<parameter=>` blocks - matching the Opus-style traces the model was distilled from. **This template requires `--tool-call-parser hermes`** (the model then emits JSON tool calls; `qwen3_xml` no longer parses them - change both together or tools break silently). A/B on a 16-scenario C/I/H subset, same seed: 25/32 vs 22/32; the two chain scenarios that failed outright now pass 2/3 trials (temp 1.0 - these scenarios are flaky; the gain is directional, not ironclad). One line added on top of the author's template to default `preserve_thinking=true`.
2. **Known model traits the template does not fix:** TC-61 (async polling) still fails, and given two tasks in one prompt the model sometimes completes the first, then claims the second is done without issuing the call. Reproduces under both templates; mitigate by splitting tasks at the prompt level.

Final production config: **Qwopus v2 FP8 + author's fixed template (JSON tool-call serialization) + `hermes` parser**, thinking ON everywhere, no MTP, `max-num-seqs 4`, `gpu-memory-utilization 0.60`.
